# Where the build departs from the plan, and why

The plan is a discussion draft. Building it surfaced places where its numbers or mechanisms
conflict with each other, or where a measurement changed a proposal. Each entry says what the
plan says, what the build does, and the evidence. Update this file whenever the build takes a
position the plan did not.

## Traffic and calibration

| Plan | Build | Why |
| --- | --- | --- |
| Chapter 1 grows "20 → 320 req/s, roughly exponential", with the process past 75% "near 190 req/s, around 3:00" | Chapter 1 follows a logistic (word-of-mouth) S-curve reaching ~190–200 req/s at 3:00 | A pure exponential from 20 to 320 over five minutes reaches 190 only at ~4:03, and doubles every ~75 s at the end, faster than any move can finish. The plan's own timings describe growth that is fast early and slower late. |
| Listings: `GET /products?category&sort&page` | Listings also take an optional price range (`min_price`, `max_price`) | Category × sort × page is a small key space, so listing views repeated (repeat ratio ~0.6) even when browsing was meant to be a long tail. Price ranges are how faceted browsing really spreads keys, and the plan already calls listings "filtered". |
| Every listing aggregates across the category | Only "sort by rating" aggregates the whole category; newest and price sorts page first | At ~21 ms of database time per listing the database saturated long before the API, so `api-compute` could never be the first pressure. See [calibration.md](calibration.md). |
| Genesis has no index beyond keys | Genesis has `(category_id, price_cents)` | A startup adds the index its main page needs. Facets went from ~2 ms to an index-only scan. |
| Search is part of every storyline's mix | "Word gets out" sends search on 0.2% of shopper steps | A naive `ILIKE` costs 100–330 ms; at 2% it was half of all database time. Search is the seed of pain for the search storylines. |
| The `pg_trgm` search index arrives as a later tuning move | The MVP's genesis database has `pg_trgm` GIN indexes on product title and description | On the 0.65-core replica, unindexed search queued behind rating sorts and timed out even after the cache; the 2026-11-17 live run missed search's 99.5% rolling availability. A 45 s local quota benchmark with the indexes achieved the offered load and had no search calls over 2 s, versus 28 of 30 without them. The first indexed VM run completed all three moves with zero errors in 439,990 requests. This brings search indexing forward as a baseline prerequisite for the MVP; later search moves need a different pressure or a genuinely new search feature. |
| Flash sale: "half of all detail and listing views go to 20 sale products and the sale category" | 55% of detail and listing views, with a 90 s ramp; hot listings are mostly "top deals" (rating-sorted) pages | At 50% the repeat ratio sat at ~0.6, the cache's boundary. A flash sale starts abruptly, and the plan requires its hot pages to be expensive aggregates. |
| Flash sale: "520 → 700 req/s", plateau at 700 | 520 → 800 req/s (each ±15% by seed), plateau at 800 | Fitted to the playground's PostgreSQL, the flash sale costs less against chapter 2 than the local stack suggested: the rating sort is about half as expensive per product, while newest, facets, and search cost about the same. With the replica doubling read capacity, a 700 req/s sale reached 70% of the combined capacity in only some seeds, and the cache came late or never. At 800 the cache is decided at 10:45–13:05 (median 11:35, the plan's "around 11:30"), and every seed takes all three moves at the database's nominal cost and at −10%. The peak, up to ~920 req/s, is within the plan's 1,200 req/s for the crowd; `node-01`'s link carries ~15 of its ~20 MB/s there, which the next session should confirm. See [calibration.md](calibration.md#the-database-re-fitted-to-the-playground-15-november-2026). |
| "Telemetry: a key-repetition sketch for cacheable reads, a per-client top-k counter, and the writes-per-seller distribution" in the API | Computed by the node agent on `node-01` from nginx's request log | Each API pod sees only its share of keys, so per-pod sketches cannot be merged in Prometheus. nginx is the single front door for the whole run, so the edge sees every key exactly. |

## Capacity and the ledger

| Plan | Build | Why |
| --- | --- | --- |
| "The sum of all caps on a node must stay below its physical CPU" | Genesis `node-01` is overcommitted (API 1.0 + PostgreSQL 1.5 + nginx and agent ≈ 2.8 cores on 2 vCPU); the rule applies to everything the architect adds | The plan's own genesis puts these caps on one 2-vCPU VM. A young product's single box running everything is the point; it is also why "scale up first" loses in the first decision record. |
| Genesis API unit: `CPUQuota=100%`, "the GIL gives it a natural ceiling of one core" | `CPUQuota=40%` on the playground; the local stack keeps one core | A playground vCPU runs the API about 2.4 times faster than the local stack the storyline is calibrated on (1.8 ms of CPU per request against 4.3 ms, on two sessions). With a full core, genesis peaked near 50% of its ceiling in chapter 1: Move 1 armed only on the forecast, at 3:50–4:45, and one seed of five never armed. The plan scales capacity units by caps ("CPU caps make this scale almost linearly"), and raising the rates 2.4 times would fill `node-01`'s ~20 MB/s link. Pods keep their 1-core limit, so the fleet has more headroom than the twin assumes; the architect's model still books 1 core for the genesis process, which Move 1 frees. See [calibration.md](calibration.md#rebuilt-images-on-a-fresh-session-14-november-2026). Approved by the owner on 2026-11-15. |
| Database instance `db.medium`: "1.5 cores … systemd `CPUQuota=150%`" | `CPUQuota=65%` for the primary and each replica on the playground; the ledger, the contracts, and the local stack keep 1.5 cores | On the playground, PostgreSQL costs about a third of what the local stack measured (1.2–1.5 ms of cgroup CPU per front-door request mid-run, against ~3), so at 150% the database never reached 70% of its cap in chapter 2: all three acting storylines took only the fleet. The twin, re-fitted to the playground's per-statement costs, puts one db.medium at 65% of a playground core: the storyline then takes fleet → replica → cache in 100 of 100 seeds, with every 5-minute window at or above 99.5% availability, and holds within about ±10% of that cost. As with the API's 40%, these are the storyline's capacity units: the ledger still books 1.5 cores, so `node-01` has no spare CPU after Move 1 and "scale up first" loses as the plan's decision record says; the scale-up move raises the quota to 87%, which is 2.0 of those cores. It also stops the overcommit measured on `node-01`, where a 150% database and nginx at ~740 req/s outran two vCPUs. See [calibration.md](calibration.md#the-database-re-fitted-to-the-playground-15-november-2026). |
| API pod: request 700m, limit 1000m; HPA 2–6 | Request 600m, limit 1000m | Six pods at 700m (4.2 cores) do not fit on `node-02` and `node-03` (3.8 allocatable). Three 600m pods per node do. |
| The API fleet waits for 75% current CPU or a two-minute forecast of 80% | The forecast arms at 60%; sustained live traffic above 30 req/s at 25% current API CPU also arms it, with a 20 req/s floor. The 30 s evidence, readiness checks, and staged traffic shifts remain | A 2026-11-19 automatic-start run chose the fleet at 2:55 and read p95 reached 780 ms at 4:00. Lowering the forecast to 60% moved it earlier, but a 2026-11-20 unattended repeat chose the fleet around 2:15 and still reached 1,094 ms read p95 at 3:00 as the legacy API served too much of that minute. Forecast timing varied with the two-minute history; measured traffic and CPU give a direct leading trigger while the traffic floor blocks idle telemetry. `make test` passes, and a 100-seed twin sweep retains the full three-move path with fleet decisions from 1:35 to 2:00 and 100% modeled worst five-minute availability. A rebuilt-image live check remains. |
| Move 2 routes eligible reads "10% → 50% → 100%" to the replica | At 100% the primary stays in the read pool at half a replica's weight | Move 3 triggers at 70% of the primary's and replica's *combined* read capacity. With every eligible read on the replica, the replica passes its cap long before then while the primary idles with writes and token-carrying reads. |
| `db-read` triggers both the replica and cache from CPU pressure | `db-read` triggers the replica from primary CPU, forecast pressure, or sustained read-majority traffic above 280 req/s before a replica exists; a separate `read-reuse` pressure triggers the cache | Once the replica unlocks its reserved 1.5 cores, CPU pressure can clear even as hot reads grow. The separate repeat signal keeps cache selection autonomous and measurable. A cooler primary on a 2026-11-20 automatic repeat delayed the replica decision to 8:10, 110 s later than the standalone trial on the same image. The new read-heavy traffic lead signal addresses that variance without waiting for a CPU bottleneck. |
| Every `db-read` arm uses one 45 s evidence window, and the cache rolls out with 15 s holds | The replica still needs 45 s of `db-read` evidence; `read-reuse` needs 5 s, and the cache shifts 10% → 50% → 100% with a 5 s hold and convergence check at each step | The first indexed VM run had no errors but read p95 reached 483 ms in the minute ending 13:00 while the cache was still migrating. Shorter cache holds helped. A later 15 s post-replica cooldown and 0.3 repeat threshold brought the cache forward, but seed 727274 still had a 340 ms read p95 at 11:00 and two search timeouts while the replica spent 86% of that minute throttled. The final progression protects reads during the replica move and uses repetition to choose the cache. |
| A cache requires a 0.6 repeat ratio | After a replica exists, the cache can be chosen at a rising 0.3 repeat ratio; without one, it still requires 0.6 | The 2026-11-18 live trial chose cache at 11:52, too late for 12:00. A 0.4 post-replica threshold passed an early ten-run gate, but a later rebuilt-image gate missed one 12:00 latency window at 271 ms when the quota lift landed at 11:38. The 0.3 threshold moved it earlier; a fresh ten-run seed-1003 gate passed all runs, with the former failing ninth run at 72 ms. Seed 727274 still hit 340 ms read p95 and two search timeouts at 11:00 before cache relief. The final progression uses the 0.3 repeat ratio as its own measured `read-reuse` pressure while CPU headroom is unlocked during the replica move, before traffic is routed there. Cache verification checks the hit ratio rather than requiring a wide margin above the repeat threshold at the decision. |
| The primary waits until 70% of its CPU ceiling before `db-read` arms | The CPU threshold is 60%, with 45 s of sustained evidence; sustained read-majority traffic above 280 req/s can also lead the replica move | On the first rebuilt-image repeatability trial, the 70% signal did not stay up until 8:43 and read p95 reached 706 ms while the replica backed up. Lowering it to 60% moved one seed-1003 decision to 6:20, but another automatic repeat decided at 8:10 when the primary was cooler. A 100-seed twin sweep with the traffic lead takes the full three-move path in every seed and chooses the replica from 5:15 to 6:15, with 100/100 validation passes. |
| The cache move adds only Valkey | The read-replica move raises the primary and replica CPU quotas from 0.65 to their full 1.5-core reservations before routing reads; rollback restores 0.65 | A seed-1003 ten-run gate passed when the cache raised these quotas, but seed 727274 exposed two search timeouts and 340 ms read p95 before that lift. The replica spent 86% of 10:00–11:00 throttled at its 0.65-core quota despite spare physical CPU. Raising the already-reserved quotas during the replica move protected reads before the cache decision: the next seed-727274 VM run had zero errors, 17/17 compliant latency windows, and 12 ms read p95 at 11:00. The cache is then chosen from measured read repetition rather than waiting for another CPU bottleneck. |

## The architect

| Plan | Build | Why |
| --- | --- | --- |
| Pressures arm on current values; forecasting (principle 7) is for slow components such as a search index | `api-compute` and `db-read` also arm on a two-minute linear forecast | The fleet and the replica take about two minutes to relieve, and traffic can double in that time. Without lead time the twin showed the single process failing requests before the fleet took traffic. |
| "Before each step, check SLO burn and the fleet's own error rate" | The fleet's guard is the fleet's own 5xx share (`api.fleet_error_ratio`), measured per upstream at the edge | Errors from the overload the move exists to cure tripped a global-error guard, which paused the move and rolled it back in the twin. |
| Error budget: 0.5% of the run's requests | 0.5% of the run's *projected* requests: so far, plus the current rate for the rest of a nominal 15 minutes | Counting only requests so far made a handful of early errors look like a spent budget, which blocked every later move. The plan's own example budgets "about 2,000 failed requests" for the whole run. |
| With under 25% of the error budget left, only protective moves are allowed; the plan includes scale-out in that category | The three MVP architecture contracts keep their `architecture` class and explicitly set `budget_protective: true`; the flag requires a rollback | In the first 90-second delayed control on 2026-11-18, the API's availability fell to 92% at 4:00, but the architect rejected the fleet because the class-only guard considered no MVP move protective. It then rejected every recovery attempt and availability fell near zero. The corrected control chose the fleet with only 1.37% of budget left, verified fleet and replica, and deliberately breached the SLO (50.87% worst full five-minute availability, 6/17 compliant latency minutes). The explicit flag lets proven, reversible pressure-relieving moves act during a budget crisis while unmarked tuning moves remain gated. |
| A 60 s cooldown follows every move | A verified read replica has a 15 s cooldown; rollbacks and other moves keep 60 s | In a 2026-11-19 automatic-start VM run, the replica verified at 10:45. Flash-sale repetition crossed the cache's 0.4 shape boundary before the global cooldown expired, but the cache could not be chosen until 11:45. Its CPU buffer came too late: read p95 reached 449 ms at 12:00, leaving 16/17 compliant latency minutes despite zero errors in 442,167 requests. The per-contract cooldown allows the next sustained pressure to be acted on sooner while the cache still requires its shape and evidence. |
| Verification compares measured relief with the prediction | CPU-ratio targets are scaled by traffic growth before comparing | The replica "under-delivered" only because traffic grew 34% between the decision and verification. |
| Step state persisted in SQLite | Persisted in one JSON file replaced atomically, plus the event stream | One writer and a small state; the same restart guarantee without a database dependency. Revisit if the run report needs queries. |

## Playground

| Plan | Build | Why |
| --- | --- | --- |
| A replica's base backup is a step like any other | `pg_basebackup --max-rate=6M`, and the step's timeout is 180 s | `node-01`'s link carries ~20 MB/s, and an uncapped backup took all of it for 15 s, timing out ~3,500 requests at ~450 req/s. The cap leaves the shop ~14 MB/s and makes the backup take 45–55 s, which the twin now models (`replicaReady` 55 s). See [calibration.md](calibration.md#first-playground-runs-13-november-2026). |
| Nodes keep the image's default time sync | chrony on every VM; `ops-01` serves the nodes, which use no other source | Cross-node timestamps (queue time from nginx's `X-Request-Start`, a replica's replay lag) need clocks within well under a millisecond. Independently synced VMs were 10–20 ms apart, enough to fail the fleet's 10 ms queue check with no queueing at all. |
| "A fresh playground is simpler" for repeated runs | `e2e/reset_genesis.py` restores a checksummed, seeded PostgreSQL cluster and shrinks the architecture to genesis in about 20 s | A fresh private session uploads 3–4 GB and takes ~12 minutes; repeated gates need identical input rows. Earlier resets kept reviews from prior runs, which made rating sorts dearer and moved decision times. The node image now carries a clean cluster snapshot; the 2026-11-17 live reset verified its checksum and exactly 50,000 products. Published playgrounds still start fresh. |
| Image updates are only needed before a run | The private overlay updater preserves `/var/lib/prometheus` when replacing an ops image; the narrator reads settled run totals at a fixed time after the story ends | A 2026-11-19 ops update erased the Prometheus time series while the crowd and architect kept their completed-run state. Preserving the time series restored all 17 historical latency windows and move records across the next update. A later restart reset the crowd's process-local counters, so an instant query reported only 28,452 requests instead of 442,167; querying the recorded total at run end plus one minute recovered the settled count. This lets the completed report survive a service restart and image update. |
